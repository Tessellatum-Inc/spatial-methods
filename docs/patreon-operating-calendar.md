# Spatial Methods — Patreon operating calendar

## Monthly production cycle

| Period | Work | Deliverable |
|---|---|---|
| Days 1–4 | Select one method from the public archive; confirm prerequisites and learning outcome | Release brief |
| Days 5–10 | Prepare explanation sequence, worked example and diagrams | Draft lesson |
| Days 11–15 | Build exercises, hints and worked solutions | Practice set |
| Days 16–19 | Test commands/notebooks, verify links and check attribution | Reproducibility record |
| Days 20–23 | Edit for clarity and accessibility; prepare member post | Publication package |
| Days 24–26 | Publish and host the discussion prompt | Member release |
| Days 27–30 | Review questions, engagement and next topic | Monthly digest and improvement notes |

This is a planning rhythm, not a promise to publish on fixed dates before the first cycle has been tested. The public technical source is corrected first whenever a substantive technical issue is found.

## Roles

- **Editor/maintainer:** selects scope, checks technical alignment and publishes corrections.
- **Learning designer:** turns the method into outcomes, examples, practice and reflection.
- **Community host:** keeps discussion useful, welcoming and within scope.
- **Contributors:** suggest topics, report issues and share reproducible examples.

One person may hold several roles. Do not imply a larger staffed team than actually exists.

## Member support boundaries

- Answer questions in the relevant shared thread where possible so the answer helps other learners.
- State a realistic response window in Patreon page settings; do not promise instant replies.
- Redirect bug reports and canonical technical corrections to GitHub issues.
- Do not request confidential data, credentials or proprietary client files.
- Research Circle feedback is group feedback on a defined artefact, not consulting.
- Any separate paid service must have its own scope, price, terms and delivery agreement.

## Quarterly Research Circle

1. Publish a short brief and a concrete learning objective.
2. Invite members to submit a small, non-confidential artefact or question.
3. Select a manageable set of examples and state selection criteria.
4. Host a 60–90 minute group workshop.
5. Publish a concise recap, useful links and unanswered research questions.
6. Ask members what should change for the next quarter.

## Content quality gates

Before publication:
- the linked public method exists and is current;
- learning outcomes and prerequisites are explicit;
- all code/notebook commands and expected outputs have been checked;
- diagrams and data have suitable rights and attribution;
- solutions are correct and explain reasoning;
- limitations and failure cases are visible;
- the page works on mobile and does not rely on colour alone;
- benefits match tier access settings and actual delivery promises.

## First-cycle review

At the end of 30 days, record:
- members by tier;
- new members and cancellations;
- posts opened or downloaded, where visible;
- exercise participation and discussion questions;
- workshop interest;
- production hours and bottlenecks;
- one improvement for the next month.

Keep the tier structure stable during the first cycle unless a material problem makes a benefit impossible to deliver.
